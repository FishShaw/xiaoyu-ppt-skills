# Narrative Routing

Choose the structure that serves the audience's job. Architecture, background, or chronology is supporting context unless it is the requested subject.

| Audience job | Recommended sequence |
| --- | --- |
| Make a decision | recommendation → constraints → options → trade-offs → risks → next actions |
| Understand a case | context → problem/task → decisions/actions → evidence/result → transfer |
| Learn a procedure | learning outcome → recognition → ordered steps → roles/handoffs → exceptions → practice/recap |
| Review research | question → evidence → method → findings → limitations → next decision |
| Approve a proposal | problem → opportunity → proposed approach → value → scope → implementation → decision needed |
| Track delivery | goal → current state → variance → causes → risks → recovery actions → owner/decision |

## Page contract

For every slide write, before layout:

- conclusion: one sentence the audience should retain;
- evidence: source or clearly marked assumption;
- relationship: comparison, sequence, hierarchy, mapping, trend, or decision;
- visual: the smallest form that exposes that relationship;
- visible copy: only what is needed to understand the conclusion;
- status/ownership: when the distinction changes interpretation;
- QA risk: dense text, connector geometry, image crop, chart scale, or version preservation.

If a slide cannot be reduced to one conclusion and one dominant relationship, split or simplify it.

## Form rules

- An executive deck should lead with a recommendation, not a ceremonial title page.
- A training deck should optimize recall and action, not completeness of the manual.
- A case deck should show decisions and trade-offs, not only system or project description.
- A research deck should show limits and next decisions, not convert uncertainty into certainty.
- A technical diagram earns a full slide only when understanding it is necessary for the audience's task.
